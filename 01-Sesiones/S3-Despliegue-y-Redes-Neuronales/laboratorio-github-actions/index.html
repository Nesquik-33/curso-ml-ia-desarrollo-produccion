Laboratorio de GitHub Actions: romper y arreglar

En tu fork y tu Codespace: un workflow que ejecuta las pruebas del proyecto en cada git push. Lo verás en verde, lo romperás a propósito, leerás el registro y lo devolverás al verde.

Lo que vas a hacer

Verde → rojo → verde, en ocho pasos

Los pasos

  1. Crear la rama lab/actions-s3
  2. Añadir .github/workflows/pruebas-proyecto.yml
  3. git push
  4. Ver el run en verde en la pestaña Actions
  5. Romper una regla con un cambio de una línea
  6. Ver el run en rojo y leer el registro
  7. Arreglarlo con git revert
  8. Ver el run en verde otra vez y el historial

Al terminar sabrás

  • Qué es CI (integración continua) y para qué sirve.
  • Leer un workflow: cuándo se dispara, dónde corre, qué pasos hace.
  • Encontrar en el registro qué prueba falló y por qué.
  • Arreglar el código, no la prueba.

Concepto · en un minuto

CI: cada cambio se comprueba solo

CI

Continuous Integration, integración continua: cada cambio que subes se comprueba solo, en una máquina limpia, con las mismas órdenes de siempre.

Sin CI

«En mi máquina funciona». Las pruebas se pasan cuando alguien se acuerda, y un fallo aparece semanas después sin saber qué cambio lo trajo.

Con CI

Cada git push deja un resultado verde o rojo, con su registro, visible para todo el equipo. Sabes qué cambio rompió qué.

Concepto · seis palabras

Workflow, disparador, runner, job, paso y run

PalabraQué es
workflowarchivo YAML en .github/workflows/: cuándo y qué ejecutar
disparador (on:)el suceso que lo pone en marcha: un push, un pull request, un botón
runnerla máquina que presta GitHub; aquí, Linux nueva y vacía
jobun trabajo del workflow; corre en un runner
paso (step)cada orden o acción del job, en orden; si uno falla, el job se para en rojo
rununa ejecución concreta, con su registro

Dónde va

En la raíz de tu repositorio: .github/workflows/pruebas-proyecto.yml. Con el punto delante de .github. Si está en otra carpeta, GitHub no lo ve.

De dónde se copia

Copiar el archivo (arriba a la izquierda) copia el archivo completo, con sus comentarios. Es el mismo que pruebas-proyecto.yml de esta carpeta.

No hay que entenderlo todo ya: las dos diapositivas siguientes lo leen línea a línea.

Anatomía · 2

Los cuatro pasos del job

1 · uses: actions/checkout@v4

Una acción ya hecha (código de otro, versionado con @v4): descarga tu repositorio en el runner, en el commit que acabas de subir.

2 · uses: actions/setup-python@v5

Instala Python 3.11, el del curso. cache: pip guarda los paquetes descargados: el segundo run descarga menos.

3 · pip install -r requirements-dev.txt

Las mismas versiones que el entorno del curso; luego pip install -e . --no-deps instala el paquete ia_mlops. working-directory hace que todo corra dentro de 04-Proyecto-Base.

4 · python -m pytest -v …

Las pruebas, con -v para ver una línea PASSED o FAILED por prueba. Si una falla, pytest termina con error, el paso se pone en rojo y el run también.

uses: = usar una acción hecha · run: = ejecutar órdenes de terminal, igual que en tu Codespace.

Decisión · el subconjunto rápido

Tres archivos de pruebas, sin datos descargados

ArchivoQué comprueba
tests/test_raw_y_master.pyla ingesta: capas RAW y MASTER
tests/test_fs_y_ml.pylas variables (FS) y el conjunto del modelo (ML), por fecha de corte
tests/test_interfaz.pyla interfaz de S2: ids → variables → modelo → recomendación, y la regla de negocio de tramos

Por qué estas

  • tests/conftest.py construye las bases desde la muestra del repositorio: no hay que descargar datos ni ejecutar antes el pipeline.
  • No necesitan Docker ni ejecutar cuadernos (esas pruebas están marcadas lento).
  • En test_interfaz.py está la prueba que vamos a romper.

Cuánto tarda

En local (Windows): test_raw_y_master 6,8 s y test_fs_y_ml 4,5 s. En el Codespace (Linux): 45 pruebas en 21 s. En GitHub (20/11/2026): el run completo, 1 min 16 s el primero y 51 s – 1 min 6 s con la caché de pip; instalar dependencias es lo más largo (38–46 s) y las pruebas, 11–12 s.

Antes de empezar

Tu fork, tu Codespace y Actions activado

1 · Fork

Si no tienes tu copia del repositorio del curso en tu cuenta, créala con Fork. El laboratorio se hace en tu fork: los runs corren en tu cuenta.

2 · Codespace

Ábrelo desde tu fork, en develop. Trabaja en la raíz: /workspaces/<tu-repositorio>.

3 · Actions en el fork

En los forks, GitHub puede tener Actions desactivado al principio. Entra en la pestaña Actions: si ves un aviso que pide activar los workflows, acéptalo. Si no hay aviso, nada que hacer.

Terminal del Codespace · en la raíz del repositorio
$ git switch develop
$ git pull
$ git status

Qué debes ver

  • On branch develop y nada pendiente.
  • Si git status enseña cambios tuyos de otras sesiones, haz commit o guárdalos antes (git stash).

Paso 3 · subir

Commit y push: aquí se dispara

Terminal del Codespace

Qué debes ver

Paso 5 · una línea

Romper la regla de negocio con una línea

La regla

En 04-Proyecto-Base/ia_mlops/config.py, SEGMENTOS_RECOMPRA: un cliente es alta desde una probabilidad de 0,70. La subimos a 0,75 sin avisar a la prueba.

Terminal del Codespace · en la raíz del repositorio
$ sed -i "s/'desde': 0.70/'desde': 0.75/" 04-Proyecto-Base/ia_mlops/config.py
$ git diff
$ git commit -am "Rotura a propósito: el tramo alta empieza en 0,75"
$ git push

Qué debes ver

  • git diff: una sola línea cambiada, 'desde': 0.70 → 'desde': 0.75.

Paso 6 · leer el log

Leer el registro: qué prueba, dónde y qué esperaba

E       AssertionError: assert ['alta', 'med...baja', 'baja'] == ['alta', 'alt...baja', 'baja']

Cómo leerlo

  • FAILED tests/test_interfaz.py::test_la_regla_de_negocio: qué prueba.
  • La prueba pide que 0,70 (segunda de la lista, índice 1) sea alta.
  • At index 1 diff: 'media' != 'alta': obtuvo media, esperaba alta.
  • El resto sigue en PASSED: el fallo está acotado.

Paso 6 · decidir

¿Está mal la prueba o está mal el cambio?

Arreglar el código

El umbral 0,70 es una regla de negocio acordada con quien hace la campaña. El cambio no estaba acordado: se deshace.

No: borrar o retocar la prueba

Quitar la prueba pone el run en verde y esconde el problema. La prueba existe justo para proteger esa regla.

Si el negocio decide cambiar el umbral, se cambian a la vez la regla y la prueba, en el mismo commit, y el run verde lo deja documentado.

Paso 7 · git revert

Arreglar: deshacer el cambio con un commit nuevo

Terminal del Codespace
$ git revert --no-edit HEAD
$ git log --oneline -3
$ git push

Qué debes ver

  • git revert crea un commit nuevo («Revert …») que deshace el anterior.
  • git log: los tres commits, el del workflow, la rotura y el revert. El historial no se reescribe.
  • Otra forma: editar la línea a mano de vuelta a 0.70, git commit -am "…" y git push.

Comprueba que lo tienes

Cinco preguntas

1. ¿Qué líneas deciden cuándo se ejecuta?

on: push: branches: ['lab/**'] (y workflow_dispatch para lanzarlo a mano).

2. ¿Por qué permissions: contents: read?

Mínimo privilegio: el workflow no necesita escribir nada.

3. ¿Por qué sale verde sin tu entorno conda?

Porque instala todo desde requirements-dev.txt en una máquina limpia: justo lo que comprueba.

4. El run sale rojo: ¿dónde miras primero?

En el paso rojo: la línea FAILED y las líneas E de debajo.

5. ¿Por qué no se arregla borrando la prueba?

Porque protege una regla acordada: borrarla esconde el problema.
